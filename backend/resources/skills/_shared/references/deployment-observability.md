# 部署与可观测性面试重点（容器、发布、监控与排障）

## 进程与容器
- 应用进程需正确处理启动、健康检查、优雅停止和退出码；容器内不要依赖不可控的后台守护进程。
- 镜像关注可复现构建、最小运行时、非 root 用户、漏洞扫描和依赖锁定，而不只追求体积小。
- CPU 限额可能造成 throttling，内存超限会触发 OOM；线程池和连接池配置必须结合容器资源上限。
- 本地磁盘通常不应保存持久业务状态，日志写标准输出，文件进入对象存储或持久卷。

## Kubernetes 与服务生命周期
- readiness 决定是否接流量，liveness 用于判断是否需要重启，startup probe 保护慢启动应用。
- Deployment 滚动升级要结合 `maxUnavailable`、`maxSurge`、终止宽限期和连接排空。
- requests 影响调度，limits 约束运行资源；HPA 的指标、冷却时间和下游容量必须一起设计。
- 配置与 Secret 分离，变更需要版本化、审计和轮换；不要把密钥烘焙进镜像。

## 发布与回滚
- 蓝绿发布切换简单但资源成本高；金丝雀发布控制风险但需要流量标记和指标判定。
- 数据库变更采用向前兼容步骤：先扩展 Schema，再发布兼容代码，迁移数据，最后清理旧字段。
- 特性开关应有负责人、过期时间和清理机制，避免永久分支增加测试组合。
- 回滚不能只回应用版本，还要考虑数据库、缓存、消息格式和外部副作用是否可逆。

## 可观测性
- 日志、指标、追踪用于回答不同问题；统一 trace/request ID 才能串联一次请求的完整路径。
- RED 关注请求率、错误率和时延，USE 关注资源利用率、饱和度和错误。
- 监控线程池、连接池、队列积压、GC、事件循环延迟和依赖调用，而不只看 CPU 与内存。
- 告警应面向用户影响和可操作性，设置持续时间、聚合、抑制和升级路径，避免告警风暴。

## 故障排查
- 先确认影响范围和最近变更，再按入口、应用、依赖、数据和基础设施逐层缩小范围。
- 使用时间线关联发布、流量、错误率、长尾延迟和资源饱和，区分根因与伴随现象。
- 止损动作需要明确副作用：限流、降级、扩容、摘流量、回滚或关闭非核心功能。
- 复盘输出触发条件、检测缺口、响应过程和长期行动项，不以“人为失误”结束分析。

## 场景与追问
- 发布后错误率缓慢上升但平均延迟正常，如何判断是否回滚？
- Pod 频繁重启但日志没有异常，下一步检查哪些系统信号？
- 连接池耗尽时，扩容应用为什么可能让数据库更快雪崩？
- 如何为一个新接口定义 SLI、SLO、告警和容量基线？
