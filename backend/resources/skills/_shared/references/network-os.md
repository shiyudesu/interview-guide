# 网络与操作系统面试重点

## 网络分层与寻址
- 能从 DNS、ARP/邻居发现、路由、TCP/TLS 到 HTTP 解释一次请求，而不是只背 OSI 层级。
- DNS 关注递归与迭代查询、缓存和 TTL、负缓存、主备解析及故障切换风险。
- NAT、四层/七层负载均衡、正向/反向代理解决的问题不同；代理链还要处理真实来源和超时预算。
- MTU 与分片会影响吞吐和连接稳定性，隧道、容器网络下需关注额外封装开销。

## TCP、UDP 与 HTTP
- TCP 三次握手确认双向收发能力；四次挥手、半关闭、TIME_WAIT 与端口耗尽需要结合连接角色分析。
- 滑动窗口、拥塞窗口、慢启动、快速重传和重传超时共同影响吞吐，不能把丢包等同于带宽不足。
- 粘包/拆包来自字节流语义，应用协议通过长度字段、分隔符或固定长度划分消息。
- HTTP/1.1、HTTP/2、HTTP/3 关注复用、队头阻塞、头压缩、连接迁移和部署兼容，而不是只比较协议版本。
- TLS 需要解释证书链、主机名校验、密钥协商、会话恢复和终止位置。

## 进程、线程与调度
- 进程提供资源隔离，线程共享地址空间；协程在用户态调度，是否并行取决于运行时和执行器。
- 上下文切换、锁竞争、缓存失效和调度延迟都会造成尾延迟，增加线程数不一定提升吞吐。
- 死锁需要同时满足互斥、持有等待、不可剥夺和循环等待；排查应结合线程栈和锁等待关系。
- 容器 CPU quota 可能导致 throttling，看到 CPU 使用率不高也可能发生延迟抖动。

## 内存、文件与 I/O
- 虚拟内存通过页表映射，缺页、中断、换页和 NUMA 都可能影响延迟；RSS 与虚拟地址空间含义不同。
- Page Cache 加速文件访问，也可能挤压应用内存；脏页回写会形成周期性 I/O 抖动。
- select/poll 每次扫描描述符，epoll/kqueue 由内核维护就绪集合；边缘触发要求读写到暂时不可继续。
- mmap、sendfile、splice 等减少数据复制或上下文切换，但仍需考虑页错误、生命周期和适用平台。
- fsync、fdatasync 和数据库 WAL 的持久化语义不同，成功写入用户缓冲区不代表断电可恢复。

## Linux 生产排障
- CPU 高先区分用户态、内核态、I/O wait、steal 和单核热点，再看线程栈、火焰图与系统调用。
- 内存问题区分堆增长、Page Cache、文件映射、内核内存和泄漏，避免看到 free 低就立即重启。
- 网络排查关联连接状态、重传、丢包、队列、DNS、握手耗时和应用超时，不能只用 ping 下结论。
- 磁盘问题关注延迟、队列深度、吞吐、空间和 inode；日志暴增与临时文件也会造成故障。

## 场景与追问
- 大量 TIME_WAIT 或 CLOSE_WAIT 分别说明什么？如何定位责任方？
- 服务 P99 升高但 CPU 平均值正常，下一步看哪些调度、网络和 I/O 指标？
- epoll 已经支持高并发，为什么应用仍可能被线程池或连接池限制？
- 容器内存持续增长，如何区分应用堆、直接内存和 Page Cache？
