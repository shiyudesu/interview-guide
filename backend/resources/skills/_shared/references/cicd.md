# CI/CD 与发布工程面试重点

## 流水线设计
- 流水线从源码、依赖、测试、制品到部署都应可追溯，同一提交应产生不可变制品并在环境间晋级。
- 快速检查前置，慢速集成与端到端测试分层执行；并行化要避免共享环境和测试数据冲突。
- 缓存用于加速依赖和构建，缓存键必须包含锁文件、工具版本和平台，不能缓存不可信执行结果。
- 失败步骤应明确阻断还是告警，不能用忽略错误或无限重试制造假绿。

## 制品与供应链
- 制品包含版本、提交、构建环境和依赖信息；镜像使用 digest 部署，避免可变 tag 漂移。
- CI 使用最小权限和短期凭证，不让来自 Fork 或不可信分支接触生产 Secret。
- 依赖扫描、SBOM、签名和来源证明降低供应链风险，但必须有漏洞处置和例外流程。
- 构建与部署权限分离，生产发布保留审批、审计和紧急回滚通道。

## 发布策略
- 滚动发布资源成本低；蓝绿切换和回滚直接；金丝雀依赖可靠的流量切分与指标判定。
- 特性开关将部署和功能发布解耦，但需要生命周期管理、默认安全值和组合测试。
- 数据库采用 expand/migrate/contract，确保新旧应用同时运行时 Schema 和消息格式兼容。
- 自动回滚应依据用户影响指标并设置观察窗口，避免短暂噪声导致发布振荡。

## GitOps 与环境治理
- 声明式配置通过审查和控制器收敛实际状态；需要处理漂移、密钥、紧急变更和回滚语义。
- 开发、预发和生产尽量保持构建产物一致，差异通过配置表达并经过验证。
- 临时环境要有配额、过期清理和数据隔离，避免成本失控或使用真实敏感数据。

## 场景与追问
- 测试全绿但上线失败，如何证明制品、配置和环境之间哪里发生了漂移？
- 数据库迁移不可回滚时，应用发布策略应如何设计？
- 金丝雀实例指标正常但整体错误率升高，可能遗漏了哪些分组？
- 如何防止 CI 中的第三方 Action 或构建脚本窃取发布凭证？
