# PostgreSQL 面试重点（MVCC、索引、执行计划与运维）

## MVCC 与事务
- 每个行版本携带事务可见性信息，快照决定当前事务能看到哪些版本；更新通常产生新版本而非原地覆盖。
- Read Committed 每条语句获取新快照，Repeatable Read 通常在事务内保持一致快照；Serializable 会检测危险并发并可能要求重试。
- 长事务和空闲事务会阻碍旧版本回收，导致表膨胀、索引膨胀和复制延迟。
- 行锁、表锁和 advisory lock 的语义不同；排查阻塞要查看等待链，而不是盲目终止所有连接。

## VACUUM 与存储
- VACUUM 回收不可见元组的空间并维护可见性信息；autovacuum 参数需结合写入率、表大小和业务低峰调整。
- VACUUM 通常不把文件空间立即还给操作系统；需要理解 VACUUM FULL 的强锁和重写成本。
- HOT update 在条件满足时可减少索引更新；fillfactor 会影响页内空间与更新效率。
- 防止事务 ID 回卷是运维底线，应监控年龄、冻结进度和 autovacuum 是否被长事务阻塞。

## 索引与执行计划
- B-tree 适合等值、范围和排序；GIN 常用于数组、全文和 JSONB 包含查询；BRIN 适合与物理顺序相关的超大表。
- 联合索引需要结合过滤、排序、基数和查询组合，不能机械套用最左原则。
- `EXPLAIN (ANALYZE, BUFFERS)` 同时观察估算与实际行数、循环次数、缓存命中和磁盘读取。
- 统计信息失真会导致错误计划；参数敏感、数据倾斜和相关列可能需要更细统计或扩展统计。

## 查询与数据模型
- N+1、全表扫描、大排序、重复子查询和不必要的宽行返回是常见性能问题。
- JSONB 提供灵活结构和索引能力，但高频更新、约束、关联查询仍需评估关系模型是否更合适。
- 分区用于管理和裁剪大数据集，不自动等于性能提升；分区键必须匹配主要访问和生命周期。
- 游标分页适合稳定排序和深分页，需处理复合排序键以及新增数据带来的边界变化。

## 复制与连接治理
- 流复制通常是异步的，读副本可能读到旧数据；强一致读需要路由主库或等待复制位点。
- WAL 支持恢复和复制，也会受长事务、复制槽和归档故障影响而持续增长。
- PostgreSQL 每连接成本较高，应用通常通过连接池限制并发；池大小要服从数据库总连接预算。
- 迁移大表应考虑锁级别、重写、回填节奏、双写兼容和回滚路径。

## 场景与追问
- 为什么查询突然从索引扫描变成顺序扫描？如何验证优化器判断？
- autovacuum 一直运行但表仍膨胀，可能有哪些原因？
- 只读副本延迟时，哪些业务可以继续读副本，哪些必须切主？
- 如何给亿级事件表设计分区、索引、归档和删除策略？
