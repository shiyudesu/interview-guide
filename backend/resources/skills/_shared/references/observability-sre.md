# 可观测性与事故响应面试重点

## 信号与指标设计
- Metrics 适合趋势和告警，Logs 记录离散事件，Traces 串联请求路径；三者需共享服务、版本和 trace 标识。
- RED 观察请求率、错误率和时延，USE 观察资源利用率、饱和度和错误，业务还需定义领域指标。
- 标签必须控制基数，用户 ID、请求 ID 等高基数字段放日志或 Trace，不直接作为指标标签。
- Histogram bucket 要覆盖业务延迟范围，平均值无法表达长尾；告警通常关注分位数和错误预算消耗。

## SLI、SLO 与告警
- SLI 是测量方式，SLO 是目标，SLA 是对外承诺；可用性需要从用户可见的成功事件定义。
- 错误预算把可靠性目标转化为可消费额度，用于决定发布速度和风险控制。
- 告警应针对可操作且影响用户的症状，配置持续时间、聚合、抑制、静默和升级路径。
- Dashboard 用于探索，告警用于行动，Runbook 提供应急步骤，三者不能互相替代。

## 分布式追踪与采样
- Trace 上下文需要跨 HTTP、RPC、消息和后台任务传播；异步边界尤其容易断链。
- 头部采样成本低但可能漏掉罕见错误，尾部采样可按结果保留但需要更高聚合成本。
- Span 名称和属性需要稳定、低基数并脱敏；不能把完整 SQL、Token 或个人数据无控制写入遥测。

## 事故响应
- 先确认影响范围、建立指挥角色并止损，再并行调查；所有关键操作进入时间线。
- 回滚、降级、限流和扩容都有副作用，应明确触发条件、负责人和恢复验证。
- 复盘关注技术和流程防线：检测为什么晚、影响为何扩大、恢复为何慢、哪些假设未验证。
- 自动修复要设置速率、权限、熔断和人工接管，避免故障时形成操作风暴。

## 场景与追问
- P50 正常但 P99 恶化，应如何从入口一路定位到具体依赖？
- 告警很多但故障仍由用户先发现，指标和告警设计可能错在哪里？
- Trace 采样后如何确保错误请求和高延迟请求仍有足够证据？
- 如何衡量事故响应能力是在改善，而不是只统计事故数量？
