# 流处理面试重点

## 时间与窗口
- 事件时间反映业务发生时间，处理时间反映系统观察时间；乱序场景通常依赖 watermark 判断等待边界。
- 滚动、滑动、会话窗口适合不同聚合语义；窗口大小和步长直接影响状态量与计算成本。
- 迟到数据需要定义丢弃、更新旧结果或旁路补偿，不能只调整 watermark 掩盖问题。

## 状态与一致性
- 有状态算子保存聚合、中间 Join 或去重信息，必须设置状态 TTL 并评估恢复时间和存储增长。
- Checkpoint 保存一致状态快照，故障后结合可重放输入恢复；Checkpoint 成功不代表外部副作用原子。
- Exactly-once 依赖 Source 可回放、状态一致快照和 Sink 事务或幂等，端到端边界必须明确。
- 去重通常使用业务事件 ID、状态 TTL 和唯一约束，TTL 太短会让晚到重放再次产生副作用。

## Kafka 与消费
- Partition 决定并行度和局部顺序；同一 Consumer Group 内一个 Partition 同时只分配给一个成员。
- Offset 提交位置与业务处理顺序决定丢失或重复风险；先提交再处理可能丢，处理后提交可能重。
- Rebalance、热点 Partition、消息积压和 Schema 不兼容是常见生产问题。
- 生产端 key、压缩、批次和 ACK 配置会影响顺序、吞吐、延迟及可靠性。

## 场景与追问
- 订单事件乱序到达时，如何计算最终状态并防止旧事件覆盖新状态？
- Checkpoint 一直超时，应从反压、状态大小、存储和网络哪些方面排查？
- Consumer 扩容后吞吐没有提升，Partition 和下游可能有什么限制？
- 流任务升级改变了状态结构，如何兼容、迁移和回滚？
