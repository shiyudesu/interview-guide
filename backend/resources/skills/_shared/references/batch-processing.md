# 批处理面试重点

## 执行模型
- 批任务把有界数据划分为 Stage 和 Task，宽依赖通常触发 Shuffle；并行度应结合数据量、分区和集群资源。
- 谓词下推、列裁剪、分区裁剪和合理文件大小减少扫描；小文件过多会增加元数据和调度开销。
- 数据倾斜可通过识别热点键、预聚合、拆分热点、调整分区或广播小表处理。
- 缓存只适合重复使用且收益高于存储成本的数据，错误缓存会挤压执行内存并拖慢任务。

## Shuffle、内存与性能
- Shuffle 包含序列化、网络、排序、落盘和合并成本，是大规模批任务的主要瓶颈之一。
- OOM 需要区分 Driver、Executor、堆外内存、单分区过大和收集到本地等不同原因。
- 增加资源不能修复错误数据分布；应通过执行计划、Stage 时间、spill、GC 和分区大小定位。
- Speculative execution 可缓解慢节点，但对有外部副作用的任务必须保证幂等。

## 正确性与恢复
- 任务重跑应按分区或批次覆盖，输出采用临时路径加原子提交，避免读到半成品。
- 输入快照、代码版本、参数和依赖需要可追溯，才能解释同一任务重跑结果为何变化。
- Backfill 要限速、隔离资源并验证下游容量，不能因补历史数据拖垮实时任务。
- 数据删除和更正要贯穿原始层、明细层、汇总层及下游导出。

## 场景与追问
- 一个原本 20 分钟的任务突然运行 3 小时，如何按 Stage 定位？
- 单个热点用户占据一半数据时，怎样处理 Join 和聚合倾斜？
- 任务在写出一半时失败，如何保证重跑后没有重复或脏结果？
- 大规模回填如何控制成本并避免影响当天 SLA？
