# Go 运行时面试重点

## 内存分配与逃逸
- 编译器通过逃逸分析决定值放在栈还是堆；返回局部变量指针不必然有问题，但可能增加堆分配。
- 小对象分配按 size class 管理，频繁临时对象会增加分配率和 GC 压力。
- slice 扩容、字符串转换、接口装箱和反射可能产生隐藏分配，应通过 benchmark 和 alloc 指标验证。
- `sync.Pool` 只适合可丢弃的临时对象缓存，GC 可随时清理，不能承载业务状态。

## 垃圾回收
- Go GC 以并发标记清扫为主，通过三色标记和写屏障保证并发标记正确性。
- GC 目标在内存占用、CPU 开销和暂停之间权衡；降低目标不一定改善整体延迟。
- 内存上涨要区分存活堆、待回收对象、goroutine 栈、mmap、缓存和容器统计口径。
- 大量指针对象会增加扫描成本，数据布局和对象生命周期可能比手工触发 GC 更重要。

## 调度、网络轮询与系统调用
- 阻塞网络 I/O 可由 runtime netpoll 管理；阻塞 syscall、Cgo 和长时间计算对调度影响不同。
- 调度器可抢占长任务，但代码仍应避免无界循环、锁内慢操作和不可取消阻塞。
- GOMAXPROCS 控制同时执行 Go 代码的 P 数量，不等于 goroutine 数量或服务并发上限。

## 性能诊断
- benchmark 要报告时间、分配次数和字节数，防止编译器优化掉被测逻辑，并使用稳定数据规模。
- pprof 用于 CPU、heap、goroutine、mutex 和 block 分析；trace 用于观察调度、GC 和任务时间线。
- 先用指标定位异常窗口，再抓 profile 对比正常与异常，避免只凭单次火焰图下结论。

## 场景与追问
- 接口延迟出现周期性尖峰，如何判断是否由 GC、调度或下游依赖引起？
- 一个优化减少了分配次数却降低吞吐，可能是什么原因？
- goroutine 数持续上涨时，如何找到创建位置和阻塞点？
- 什么情况下调整 GOGC 或内存上限，如何验证副作用？
