# Go 服务工程面试重点

## HTTP、RPC 与中间件
- `net/http` Server 需要配置读取头、读取、写入和空闲超时，避免慢连接长期占用资源。
- Middleware 负责认证、日志、追踪、限流和恢复，但顺序会影响上下文、错误和响应记录。
- gRPC 关注 deadline、状态码、metadata、流式调用、消息大小和负载均衡；重试前必须确认幂等语义。
- JSON 解码要处理未知字段、数字精度、请求大小和流关闭；对外契约应有版本兼容策略。

## 数据访问
- `database/sql` 本身是连接池；MaxOpen、MaxIdle、MaxLifetime 和等待指标要结合数据库总预算设置。
- 事务边界由业务一致性决定，避免在事务中进行慢网络调用；失败路径必须 rollback。
- Repository 隔离数据库细节，Service 负责编排，但不能用接口层层包裹掩盖清晰依赖。
- 批量写、游标分页和预加载用于减少往返与内存占用，同时关注锁时间和失败重试。

## 服务生命周期
- 入口请求、后台任务和消费循环统一使用 context 传播取消与 deadline。
- 优雅停止顺序通常是停止接流量、等待在途请求、停止消费者、刷新必要数据、关闭连接。
- 配置、客户端和时钟通过依赖注入提供，避免全局单例让测试和并行执行相互污染。
- 日志、指标和 Trace 应共享 request/trace ID，并对敏感字段统一脱敏。

## 测试与发布
- 单元测试使用表驱动用例和明确 fake；涉及 SQL、Redis、消息系统时使用隔离的真实集成环境。
- `go test -race` 检查数据竞争，benchmark 和 profile 用于验证性能结论。
- 编译产物可静态链接但仍需考虑证书、时区、Cgo 和系统调用兼容；容器中使用最小权限运行。

## 场景与追问
- 一个 Handler 超时返回后仍在执行数据库写入，如何修复？
- 服务启动了大量 goroutine 消费任务，如何实现背压和优雅停止？
- 数据库连接池等待升高但数据库 CPU 不高，如何定位？
- 如何设计一个可观测且不会重试放大的 gRPC 客户端？
